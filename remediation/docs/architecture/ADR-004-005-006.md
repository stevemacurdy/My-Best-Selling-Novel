# ADR-004: Lifetime Tier Surrounding-Controls Dependency Declaration

## Status
**VOIDED — 2026-05-06 by Steve Macurdy**

The lifetime tier itself was eliminated from the product (PATCH-3 sub-deliverable A.3, operator decision Q-8.2). With no lifetime SKU in the product, the dependency declaration that this ADR establishes is moot. The 6 surrounding controls listed below remain valuable for general security/compliance posture (and are still tracked in their respective R-TASK files) but no longer gate any product functionality.

The original ADR text is preserved below for audit-trail integrity per Phase 3.14.4 (no-silent-removal rule). **Do not reactivate this ADR without first reactivating the lifetime tier in Decision #7 and confirming a new operator decision.**

History: drafted 2026-05-04; confirmed 2026-05-05; **voided 2026-05-06** when operator concluded — after going through the surrounding-controls remediation work — that the lifetime SKU's long-tail liability outweighed its revenue contribution. Original surrounding-controls work continues for non-lifetime reasons:
- R-TASK-119 (refund policy) still required for monthly/annual subscriptions
- R-TASK-120 (acceptance recording) still required for ToS/Privacy/Refunds
- R-TASK-135 (email templates) ships without the lifetime variant — 7 templates instead of 8
- R-TASK-103 (admin MFA) still required for general admin security
- PATCH-002 (webhook idempotency) still required for recurring billing event dedup
- R-TASK-107 (support inbox) still required for general support

## Original Context (preserved for audit trail)

Per audit OBSERVATION-004 (LIKELY-MISMATCH), the Lifetime tier (Decision #29) introduces a $3,456.78 SKU into a system whose surrounding controls were designed for $29/month subscriptions. Customers paying lifetime prices reasonably expect:
- Refund policy with documented window (current: none specified)
- Acceptance recording for what they agreed to (current: none)
- Account hardening befitting the price (MFA at minimum)
- Subscription duration guarantees (5-year minimum to honor "lifetime" framing)
- Distinct lifetime confirmation email (current: same upgrade email as monthly)

At $29/month, an unhappy customer is annoyed for one billing cycle. At $3,456.78, they have a financial incentive to dispute, chargeback, demand refund, or pursue small-claims action. The lifetime tier raises the legal exposure ceiling on every other gap in the audit.

## Decision

**Keep the lifetime tier.** Do not enable lifetime checkout in production until the following surrounding controls are in place:

1. **Refund policy** (R-TASK-119) — explicit 14-day window + 5-year minimum guarantee
2. **Acceptance recording** (R-TASK-120) — proves what they agreed to and when
3. **Distinct lifetime confirmation email** (R-TASK-135) — references refund window, MFA recommendation, lifetime guarantee terms
4. **MFA recommendation surfaced** (R-TASK-103) — strongly encouraged in confirmation email; not strictly required
5. **Webhook idempotency** (PATCH-002) — prevents duplicate $3,456.78 charges
6. **Support inbox** (R-TASK-107) — somewhere for them to write when something goes wrong

Lifetime checkout in Stripe is **disabled in production** until all 6 are shipped. The `lib/canon.ts` `lifetime_price_usd` field can exist; the Stripe price IDs for lifetime can exist; but the `/pricing` page does NOT render the lifetime CTA buttons until the dependencies are met.

## Implementation

In `app/pricing/page.tsx`:
```tsx
const LIFETIME_ENABLED = process.env.NEXT_PUBLIC_LIFETIME_ENABLED === 'true';
// Set to 'false' in env until R-TASK-119, 120, 135, 103, PATCH-002, R-TASK-107 all complete
// Then flip to 'true'
```

This gates lifetime visibility behind a deploy-time flag, not a feature-flag system (overkill for v1).

## Rationale

The lifetime tier is a real commercial choice — annual revenue smoothing, customer-loyalty signal, premium tier for power users. Removing it costs revenue. Shipping it without the surrounding controls invites disputes that the controls would prevent.

Gating behind a flag preserves the option without the liability.

## Consequences

**Positive:**
- Lifetime tier viable post-launch when controls in place
- No accidental enablement during v1 build sessions
- Clear sequencing: 6 items must complete before flag flip

**Negative (accepted):**
- Lifetime revenue not available in first weeks of launch
- Operator must remember to flip flag (mitigated by explicit pre-launch checklist in R-TASK-141)

## Operator Confirmation

```
Lifetime tier shall remain disabled in production via NEXT_PUBLIC_LIFETIME_ENABLED=false
until R-TASK-119, R-TASK-120, R-TASK-135 (lifetime variant), R-TASK-103, PATCH-002, and
R-TASK-107 have all shipped. Pre-launch checklist (R-TASK-141) must verify all six are
complete before flag flip.

```

# ADR-005: Manual-Test Pattern with Minimum Vitest + Playwright at v1

## Status
Accepted (2026-05-04)

## Context

Per audit OBSERVATION-005 (STRONG-MISMATCH), Phase 10 of the build strategy is structured as manual checklist tests (TASK-063 through TASK-068). Every TASK file's "Tests Required" section names manual acceptance criteria. Zero automated test files in the spec packet.

This is the gap most confident to close at v1, because the manual-test pattern compounds with several other gaps:
- GAP-061 (no unit test floor)
- GAP-063 (no E2E framework)
- GAP-064 (no Stripe contract test)
- GAP-065 (no automated RLS isolation test)
- GAP-094 (manual migration paste)

Each individually is HIGH severity. As a pattern, they constitute an architectural choice — "we will verify by manual procedure" — that breaks at the 4-month mark when refactor cadence exceeds manual-test cycle time.

## Decision

**Adopt the minimum viable automated-test floor at v1, defer comprehensive E2E to v1.1.**

### v1 floor (mandatory before launch)
- **Vitest** (R-TASK-130) — unit tests for `lib/` (subscription, api-auth, password, ratelimit, audit, brand). Coverage floor: 60% of `lib/` lines.
- **Playwright** (R-TASK-131) — smoke tests for: auth flow (sign up → sign in → sign out), billing flow (test card → tier upgrade), agent S0 step
- **Stripe contract tests** (R-TASK-132) — fixtures for 6 webhook event types
- **RLS isolation tests** (R-TASK-133) — automated cross-user access tests for all 11 tables
- **Migration CI** (R-TASK-138) — fresh + seeded migration test on every PR

### Deferred to v1.1
- Full agent S0-S11 E2E coverage
- Visual regression tests
- Load testing infrastructure
- Performance budgets enforced in CI
- Accessibility automated tests on agent (depends on ADR-003)

## Rationale

The minimum floor catches the regression classes most likely to ship and most damaging when shipped:
- Stripe webhook regression (silent revenue leak)
- RLS isolation regression (cross-user data leak — catastrophic)
- Auth flow regression (lockout)
- Migration breakage (data loss)

These are non-negotiable. Beyond them, comprehensive E2E coverage is valuable but the marginal cost grows quickly with the verbatim-port directive in force (Decision #11). Deferring agent E2E coverage to v1.1 lets ADR-003 land first, after which agent components are testable.

## Consequences

**Positive:**
- v1 ships with safety net against the worst regression classes
- Test cadence matches refactor cadence for `lib/` and critical flows
- Future Claude Code sessions have something to break against

**Negative (accepted):**
- Agent regressions in v1 caught only manually
- Visual regressions caught only by post-deploy check
- Load testing happens in production (mitigated by capacity targets per R-TASK-142)

# ADR-006: REST over tRPC at v1

## Status
Accepted (2026-05-04)

## Context

Per audit OBSERVATION-006 (MARGINAL), the API surface is 11 REST routes consumed only by the own web app. tRPC (typesafe RPC) is an alternative that gives end-to-end types between server and client.

## Decision

**Keep REST.** Do not adopt tRPC at v1.

## Rationale

- One consumer (the own web app) — main argument for tRPC is multi-consumer DX, which doesn't apply
- Decision #11's verbatim-port directive locks in the agent's existing fetch() patterns; introducing tRPC creates a second pattern and a styling inconsistency
- API surface is small (11 routes) — type safety from tRPC saves hours, not weeks
- Public API for third-party integrations is in the deferred-to-v-next list (R-TASK-149); when that ships, REST + OpenAPI generation is the easier multi-consumer path

## Consequences

**Positive:**
- Single API style across the codebase
- Standard REST debug paths (curl, Postman) work without setup
- Future public API path is unblocked

**Negative (accepted):**
- Type safety between client and server requires manual sync (mitigated by sharing types via `lib/types.ts`)
- Refactors that change response shape risk silent client breakage (mitigated by R-TASK-130 unit tests + R-TASK-131 E2E tests)
